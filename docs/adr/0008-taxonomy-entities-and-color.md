# 分类与标签升级为可管理实体并持久化选色

新增分类页与标签页（菜单顺序：笔记、待办、分类、标签、设置）要求对分类/标签做完整 CRUD，这与两处既有设计冲突，定案如下：

1. **标签从值对象升级为显式实体**。原 `taxonomy.rs` 约定标签为值对象：挂载时按需建立、`set_note_tags` 每次写入后清理失去全部引用的标签。该约定下管理页无意义——用户选好颜色的标签会在下一次笔记保存时被静默清理。定案：移除孤儿自动清理路径，标签与分类同生命周期：建立后持续存在，仅经标签页显式删除。代价是标签随使用自然累积，清理由用户手动完成。

2. **颜色从按名随机分配改为持久选色**。原 `PaletteStore::color_for(name)` 洗牌袋机制按名字在进程内随机分配颜色，重启即变，且用户无法干预。定案：`categories`/`tags` 表各加可空 `color` 列存用户所选颜色；未选色（NULL）的项目在所有界面（管理页、卡片徽片、编辑器表单）以主题中性样式渲染；内置 6 色 Material 色板与任意取色器作为选色来源，色板常量保留，`color_for` 按名分配、名字映射与洗牌袋逻辑删除。代价是既有徽片默认全部转中性，颜色成为用户显式选择的持久属性。

3. **删除被引用条目的语义**：允许删除，删除时解除全部笔记关联（分类置空 `category_id`、标签清理 `note_tags`），删除前弹确认框并显示引用计数。

4. **编辑器侧分类标签表单不动**：自由输入回车即存的既有交互保留，输入已有名称自然挂到已有实体（含其颜色），输入新名称自动建实体（默认无色）。

理由：颜色与实体存续都成为确定、持久、所见即所得的属性，管理页与编辑器两入口互通；顺带消除"重启变色"的随机性。否决保留自动分配作兜底：两种颜色来源并存导致管理页显示的"自动色"每次启动可能变化、重命名后重抽，状态难以解释。

状态：accepted（2026-10-24）
